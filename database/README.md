# LSS SQL Server access schema

Target: `localhost\SQLEXPRESS`, existing database `LSSRepo` (SQL Server 2022).

## Execute in SSMS

1. Connect with your authorised Windows account and select LSSRepo.
2. Open `001_create_access_schema.sql`, review it, and Execute (F5).
3. Refresh Tables. You should see `lss.Roles`, `lss.AccessStatuses`, `lss.SystemSetup`, `lss.Users`, and `lss.AccessAudit`.
4. When ready to provision the first admin, open `002_bootstrap_admin.sql`. Verify the configured tenant ID and user Object ID before execution. Optional name/email values are descriptive only.
5. Execute the bootstrap script once. It returns the newly provisioned Approved/Admin record. No passwords or Microsoft tokens are required in these scripts.

The schema script does not create the database or modify existing tables. If any target object exists, it stops and rolls back. Re-running after successful creation intentionally fails rather than silently accepting a mismatched schema. Bootstrap refuses to run if setup/users already exist. The application should remain unavailable for registrations until bootstrap is complete.

## Tables and constraints

- Roles: None, Staff, Admin; seeded lookup values.
- AccessStatuses: Pending, Approved, Revoked; seeded lookup values.
- SystemSetup: singleton installation row, one allowed tenant, original admin identity and bootstrap audit information.
- Users: identity primary key; unique tenant/object-ID pair; tenant/role/status/self-reference foreign keys; defaults Pending/None; valid status/role combinations; positive authorization version; UTC timestamps; SQL rowversion for optimistic concurrency.
- AccessAudit: target and actor foreign keys; old/new state snapshots; action and actor-kind checks; reason; UTC timestamp; correlation ID for related events, including both sides of a transfer.
- A filtered unique index permits at most one Approved/Admin. Revoked accounts may retain their historical Admin role.
- Foreign keys use SQL Server's default NO ACTION: there are no cascading deletes that could erase audit history.
- Email is deliberately not unique and is not used to grant access. GUIDs must be nonzero. Display fields may be NULL until a provisioned user first signs in.

## Application integration

The app now uses these tables through Microsoft.Data.SqlClient. Local setup and bootstrap are complete; do not rerun the scripts. See the main README for connection settings and verification. The original JSON registry remains an unused backup; its roles are not imported.

- Only trust tenant/object IDs extracted from Microsoft-validated authentication. SQL constraints cannot validate Entra identities.
- Retrieve roles/status from SQL Server; deny access unless Approved with the required role.
- For each access change, update status/role, increment AuthorizationVersion, update access-change/UpdatedAtUtc fields, and insert AccessAudit in ONE transaction. DEFAULT timestamps apply to inserts only.
- Match the previous RowVersion in update predicates to detect concurrent edits. RowVersion is a concurrency token, not a time value or substitute for AuthorizationVersion.
- Preserve revoked users. They must not become Pending or Approved automatically at the next login.
- Ordinary revocation cannot remove the only approved administrator. This cross-row/workflow rule is NOT guaranteed by the unique index (which only prevents two admins).
- Transfer admin in one transaction: acquire the `LSS.AccessAdministration` application lock; validate actor and successor; demote the old admin first; promote the approved successor; increment both authorization versions; audit both changes with one correlation ID; verify exactly one approved admin remains; commit. A failure must roll back both updates. Do not use NOLOCK/READ UNCOMMITTED for authorization reads.
- All access-changing code must use the same transaction-owned application lock and actor authorization checks. Direct writes outside that workflow can bypass the no-zero-admin rule.
- InitialAdminUserId records history only. It must not continually re-grant rights to that person. Recovery is an operator-only, audited process, not rerunning bootstrap.
- Audit records are not automatically generated by triggers and are not tamper-proof. Use a separate restricted runtime SQL principal; deny it UPDATE/DELETE on AccessAudit and changes to setup/lookup definitions. Do not run the deployed app as dbo/db_owner. Future stored procedures can further restrict write access.

## Verification

The local LSSRepo setup was verified read-only. Integration tests execute the schema and access workflows in separate disposable SQL Express databases. Microsoft account sign-in must still be checked in the browser.

After execution, these read-only queries can confirm the created objects and seeded values:

```sql
USE LSSRepo;
SELECT name FROM sys.tables WHERE schema_id = SCHEMA_ID(N'lss');
SELECT * FROM lss.Roles;
SELECT * FROM lss.AccessStatuses;
SELECT SetupId, TenantId, BootstrapCompleted, InitialAdminUserId FROM lss.SystemSetup;
SELECT UserId, StatusCode, RoleCode FROM lss.Users;
```
